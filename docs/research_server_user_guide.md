## Как загрузить датасет

Выбор способа зависит от размера датасета и места, где он сейчас лежит.

Для небольших файлов используйте загрузку через JupyterLab:

1. Откройте JupyterHub и запустите свое окружение.
2. Перейдите в папку `/home/jovyan/work`.
3. Нажмите кнопку загрузки файлов в JupyterLab.
4. Работайте с файлами из своей личной папки.

Этот способ удобен для небольших CSV, Excel, изображений, архивов и тестовых данных. Для больших датасетов лучше не использовать браузерную загрузку: она может оборваться.

Если датасет на внешнем жестком диске или флешке, лучше передать его администратору. Администратор подключит диск к серверу и перенесет данные в одну из папок:

- `/srv/datasets/<dataset-name>` - если это общий исходный датасет, который нельзя случайно менять;
- `/srv/projects/<project-name>` - если это рабочие данные конкретного проекта, которые команда будет изменять.

Если датасет лежит в облаке, обычно лучше скачивать его сразу на сервер, а не сначала на личный компьютер:

- для прямой ссылки используйте `wget` или `curl`;
- для Google Drive, Яндекс Диска, S3 и похожих хранилищ лучше использовать `rclone`;
- для Kaggle, Hugging Face и других научных репозиториев можно использовать их CLI-инструменты или Python-код внутри JupyterLab.

Не вставляйте личные токены и пароли в общие ноутбуки. Если для скачивания нужны ключи доступа, передайте их администратору отдельно или настройте их только в своей личной рабочей папке.

Для больших датасетов заранее сообщите ответственному:

1. Название проекта.
2. Примерный размер данных.
3. Где лежит датасет: внешний диск, ссылка, облако, Kaggle, Hugging Face и т.д.
4. Нужно ли сделать датасет общим только для чтения или рабочим для изменения.

## Зачем нужен свой Docker-образ

Обычно пользователю не нужно запускать Docker-контейнер вручную. Стандартный путь работы такой:

1. Пользователь входит в JupyterHub.
2. Выбирает подходящее окружение.
3. Работает в JupyterLab с ноутбуками, скриптами и данными.

Свой Docker-образ нужен, если стандартных окружений не хватает:

- нужны конкретные версии Python, R, CUDA или системных библиотек;
- нужно воспроизводимое окружение для статьи, диссертации или гранта;
- нужно установить тяжелые зависимости, которые не стоит ставить каждый раз вручную;
- нужно запустить не Jupyter, а отдельный сервис: API, веб-интерфейс, базу данных, long-running worker;
- нужно проверить готовый Docker-образ из репозитория проекта.

Если нужен только дополнительный Python-пакет, часто проще попросить администратора обновить существующий образ, чем заводить отдельный контейнер.

## Как пользователю работать со своим Jupyter-окружением

Обычно пользователю нужен не отдельный JupyterHub, а отдельный Docker-образ или отдельный JupyterLab-контейнер.

JupyterHub - это общий вход на сервер, авторизация пользователей и управление их окружениями. Его лучше держать одним на сервер. Если каждому пользователю поднимать свой JupyterHub, появятся отдельные логины, порты, токены, настройки безопасности и больше мест, которые могут сломаться.

Рекомендуемый вариант:

1. Пользователь готовит список библиотек, `requirements.txt`, `environment.yml` или `Dockerfile`.
2. Администратор собирает Docker-образ.
3. Администратор добавляет образ в список окружений JupyterHub.
4. Пользователь выбирает этот образ при запуске своего сервера в JupyterHub.

Пример простого `Dockerfile` для образа, который будет запускаться через JupyterHub:

```dockerfile
FROM quay.io/jupyter/scipy-notebook:latest

USER root
RUN apt-get update && apt-get install -y --no-install-recommends \
    git \
    && rm -rf /var/lib/apt/lists/*

USER ${NB_UID}
RUN pip install --no-cache-dir \
    opencv-python \
    scikit-image \
    seaborn
```

Если нужна GPU, лучше брать за основу уже подготовленный CUDA-образ сервера или согласовать базовый образ с администратором.

Администратор собирает образ на сервере:

```bash
sudo docker build -t local/project-name-notebook:2026-07-07 .
```

После этого администратор добавляет образ в настройки JupyterHub, перезапускает платформу, и пользователь выбирает новое окружение при входе.

## Как запустить отдельный JupyterLab-контейнер

Отдельные контейнеры запускает администратор через Portainer или SSH. Обычным пользователям не нужно иметь доступ к группе `docker`, потому что это почти полный root-доступ к серверу.

Этот вариант нужен, если проекту требуется не стандартный запуск через JupyterHub, а отдельный долгоживущий JupyterLab, свой порт, отдельная конфигурация или нестандартный контейнер.

Перед запуском отдельного контейнера нужно согласовать:

1. Название проекта и владельца.
2. Docker-образ или `Dockerfile`.
3. Нужна ли GPU.
4. Сколько CPU и RAM можно выделить.
5. Какие папки подключить внутрь контейнера.
6. Нужно ли открывать сетевой порт.
7. Кто будет иметь ссылку и токен доступа.

Рекомендуемая схема для данных:

- `/srv/projects/<project-name>` подключать в контейнер как рабочую папку для записи;
- `/srv/datasets/<dataset-name>` подключать только для чтения;
- не хранить важные данные только внутри контейнера.

Пример `docker-compose.yml` для отдельного JupyterLab без GPU:

```yaml
services:
  jupyter:
    image: quay.io/jupyter/scipy-notebook:latest
    container_name: project-name-jupyter
    restart: unless-stopped
    ports:
      - "10.200.1.180:88XX:8888"
    environment:
      JUPYTER_TOKEN: "CHANGE_ME_LONG_RANDOM_TOKEN"
    volumes:
      - /srv/research/users/USER_LOGIN:/home/jovyan/work
      - /srv/research/projects/PROJECT_NAME:/srv/project
      - /srv/research/datasets/DATASET_NAME:/srv/datasets/DATASET_NAME:ro
    cpus: "4.0"
    mem_limit: 8g
```

В примере `88XX` нужно заменить на свободный порт, например `8810`, `8811` или `8820`. Токен должен быть длинным и случайным.

Запуск:

```bash
sudo docker compose up -d
sudo docker compose logs --tail=100
```

После запуска пользователь открывает:

```text
http://10.200.1.180:88XX
```

Если нужен GPU, в compose-файл добавляют доступ к видеокарте:

```yaml
    gpus: all
```

И используют образ, в котором есть CUDA и нужные GPU-библиотеки.

Перезапуск отдельного контейнера через Portainer:

1. Откройте Portainer: http://10.200.1.180:9000
2. Перейдите в `local -> Containers`.
3. Найдите контейнер проекта.
4. Нажмите `Restart`.
5. Если нужно посмотреть ошибку запуска, откройте `Logs`.

Перезапуск через SSH:

```bash
sudo docker ps
sudo docker restart CONTAINER_NAME
sudo docker logs --tail=100 CONTAINER_NAME
```

Если контейнер был запущен через Docker Compose, перезапускать лучше из папки его проекта:

```bash
sudo docker compose restart
sudo docker compose logs --tail=100
```

Для обычной научной работы предпочтительнее не отдельный JupyterLab-контейнер, а свой образ внутри общего JupyterHub. Так проще управлять доступом, ресурсами и пользователями.

## Можно ли подключаться без VPN

Технически это возможно, но не рекомендуется открывать JupyterHub напрямую в интернет.

Более безопасные варианты:

1. Использовать университетский VPN. Это текущий рекомендуемый вариант.
2. Настроить reverse proxy с HTTPS, доменным именем и строгой авторизацией.
3. Использовать WireGuard/Tailscale/ZeroTier для отдельной защищенной сети.
4. Использовать Cloudflare Tunnel или аналогичный tunnel-доступ с двухфакторной авторизацией.

Если нужен доступ без университетского VPN, лучше делать его через отдельный защищенный канал, а не открывать порты `8000`, `3000` и `9443` наружу напрямую.

## Правила безопасности

- Не передавайте свои пароли другим людям.
- Не запускайте неизвестные Docker-образы без согласования.
- Не храните персональные или чувствительные данные в общих папках без необходимости.
- Не удаляйте чужие файлы из проектных директорий.
- Не добавляйте обычных пользователей в группу `docker`: это фактически дает root-доступ к серверу.
