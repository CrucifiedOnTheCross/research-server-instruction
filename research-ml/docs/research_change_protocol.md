# Протокол фиксации исследовательских изменений

Этот документ задаёт обязательный порядок работы над экспериментальным кодом проекта.
Любое изменение, способное повлиять на данные, обучение, отбор моделей, метрики или
научную интерпретацию, должно быть описано в Markdown до запуска либо одновременно
с реализацией.

## Что обязательно фиксировать

Для каждого изменения или эксперимента необходимо записать:

1. Идентификатор стадии и гипотезы, например `S8-H1`.
2. Наблюдение или проблему, из которой возникла гипотеза.
3. Формулировку проверяемой гипотезы.
4. Научное и инженерное обоснование.
5. Использованные статьи с DOI или постоянными ссылками.
6. Изменённые файлы кода и конфигурации.
7. Независимую и зависимые переменные.
8. Контроли, seeds, split и правила предотвращения leakage.
9. Критерий подтверждения или опровержения, заданный до просмотра результата.
10. Структурированные артефакты: resolved config, environment, predictions и metrics.
11. Результат с неопределённостью, ограничениями и отрицательными наблюдениями.
12. Решение: принять, отклонить, уточнить или перенести гипотезу.
13. Следующую проверку, возникшую из результата.
14. Git commit с реализацией.

Логи не используются как основной источник результатов. Значения извлекаются из
`summary.json`, `*_metrics.json`, `metrics.csv`, prediction-файлов и resolved config.
Лог допускается только для диагностики сбоя, если структурированный артефакт не был
создан.

Каждая статья, реально повлиявшая на гипотезу, метод или интерпретацию, должна быть
добавлена одновременно:

- в отчёт соответствующей стадии;
- в общую Google-таблицу литературы;
- в поле `Literature` записи исследовательского журнала.

## Шаблон записи стадии

```markdown
## S<N>-H<M>: краткое название

- Status: proposed | running | completed | rejected
- Date:
- Code commit:
- Observation:
- Hypothesis:
- Rationale:
- Literature:
- Code/config changes:
- Data and split:
- Independent variable:
- Outcomes:
- Controls:
- Seeds/folds:
- Leakage safeguards:
- Predefined success criterion:
- Structured artifacts:
- Results:
- Uncertainty/statistical test:
- Limitations:
- Decision:
- Follow-up hypothesis:
```

## Правило для идей в коде

Новая исследовательская идея не должна оставаться только в комментарии, имени
конфига, TODO или shell-скрипте. Она получает идентификатор гипотезы и запись в
отчёте стадии. Технический рефакторинг без изменения поведения можно фиксировать
кратко в разделе `Engineering changes`, но изменение preprocessing, sampling,
loss, model, split, selector, metric или stopping rule всегда считается
исследовательским.

## Definition of done для стадии

Стадия завершена только когда:

- код и конфигурации закоммичены;
- критерии проверки были определены до анализа locked test;
- структурированные результаты собраны и проверены;
- отчёт стадии обновлён фактическими результатами;
- использованная литература внесена в отчёт и Google-таблицу;
- записано решение и следующая проверяемая гипотеза.
